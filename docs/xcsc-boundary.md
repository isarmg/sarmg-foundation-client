# xcsc 与产品边界

xcsc 是构建期客户端上游，不是产品功能的集中仓库，也不在生产环境形成中央服务。产品固定公共库的精确版本和完整 Git revision。

客户端使用 `xcsc::log` 获取结构化事件、UTC 时间、脱敏和有界日志查询/输出，日志层为 `xcsc::log::XcscStructuredLayer`。这些实现及必要错误原语直接属于 xcsc 单体。Linux 离线升级工具 xssc 使用同一客户端包内的显式维护功能开关。

| 所属 | 应负责 | 不应负责 |
|---|---|---|
| xcsc | 桌面、移动及离线客户端的运行时、Spool、文件与秘密安全、便携日志、原生终端输入、服务生命周期、本机只读状态通道和移动 FFI | 产品配对线上协议、远端 API 状态解释、产品错误码及恢复文案、本机第三方服务策略和管理服务端的 Web |
| 产品仓库 | 业务 DTO、端点、状态机、错误码、恢复步骤、业务页面、业务安全加强和产品发布验收 | 复制 xcsc 已发布的实现并维护第二事实源 |

一项实现只有同时满足以下条件才适合进入公共上游：

1. API 用平台概念表达，不包含 xsos、xscs、xcos、xszs 等产品名称或业务 DTO。
2. xcsc 可以独立测试它，不需要启动某个产品的协议端点或读取产品状态。
3. 产品仍能在适配器前后施加更严格的安全规则；公共实现不会把最强产品规则降成最低共同标准。
4. 按职责和通用性决定归属，而不以消费者数量作为门槛；真正通用的机制即使只有一个产品使用，也可进入对应公共上游，产品业务规则仍留在产品仓库。
5. xcsc 成为唯一实现源后，消费者通过不可变发布包使用它，不复制源码快照。

终端输入 API 只处理控制终端、输入上限、绝对期限和秘密清零，可由多个桌面客户端复用。`pairing_*` 的 HTTP 含义、用户文案和恢复步骤不符合该边界，必须由定义相应协议的产品提供。`xcsc::cli` 只负责稳定错误信封，并通过 `ProductErrorCatalog` 接收产品展示信息。

能力配置也不能把某个产品架构冒充通用要求。`desktop-client` 只要求产品提供 HTTPS 投递适配器；Spool、xcsc 私有状态、Doctor、完整服务生命周期和受保护终端输入均按实际采用情况显式声明。实时流客户端根据实际采用的机制声明能力。

通用机制还必须由实际层级承载。`xcsc::secure_xml` 提供客户端侧与产品无关的解析预算；业务 XML 协议、命名空间、设备字段和具体预算值由产品定义。


xcsc 本仓库只有一个根包，没有工作区外壳、独立子 Cargo 包或内部 path 依赖。仓库检查覆盖所有目标平台依赖及 Cargo `patch`/`replace`。产品自身可有业务工作区；消费检查解析其工作区继承、别名和所有 Cargo 清单，要求唯一官方 xcsc 包、精确版本及完整 Git revision，不能通过 `source_roots` 排除依赖检查。

`Args::parse` 解析通用选项以及产品显式声明的选项，仅为通用 `--config` 和 `--state` 验证绝对路径。产品选项的含义与路径要求由产品在命令执行前检查，可复用 `absolute`；xcsc 不依据产品选项名推断业务语义。

CLI 输出经过递归脱敏：字段名大小写和连接符不影响匹配，密码、令牌、凭据、证书及 API/私钥字段中的字符串、数字、对象或数组会整体替换为 `{"configured": boolean}`；布尔值保留，供状态标志使用。普通字符串和人类可读输出中的字段名会移除控制字符。产品应使用明确的字段名表达秘密，并且不得将秘密放入普通字段或错误详情中。
